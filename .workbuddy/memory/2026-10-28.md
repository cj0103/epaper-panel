## epaper-panel：代码审查 + 雅黑字体方案（只出方案，未动固件）

### 一、代码审查结论（按严重度，全部有源码/库源码交叉验证）

**P0-1 `display(bool)` 语义与注释双反**
- 位置：`firmware/epd_panel/epd_panel.ino:95`
  `display.display(g_hard_refresh); // true=整屏刷新清残影, false=快刷`
- 实证链：`GxEPD2_3C.h:253 display(bool partial_update_mode=false)` →
  `epd2.refresh(partial_update_mode)` → `gdey3c/GxEPD2_750c_GDEY075Z08.cpp:257`
  `refresh(bool)`：`if (partial_update_mode) refresh(0,0,W,H); else _Update_Full();`
- 结论：**`true` = 局部/快刷（留残影），`false` = `_Update_Full()` 整刷（清残影）**，
  与固件注释完全相反。连带 `epd_panel.ino:213-215` 的"每 4 次快刷后整刷一次"
  计数逻辑和 `api_panel.cpp:290/299` 的"首末页整刷"判断一起反向。
- 修法：`display.display(!g_hard_refresh)` 或把变量改名成 `g_partial_mode`，
  并把 `loop()` 里的计数条件、API 里的首末页判断一并对齐。

**P0-2 `scribeBuildRows` 行号 uint8_t 溢出**
- 位置：`render_panel.cpp:351-357`
  `static uint8_t scribeBuildRows(...)` + `uint8_t row = 0;` +
  `while (ci < total && row < SCRIBE_MAX_ROWS - 1)`（SCRIBE_MAX_ROWS=340）
- 根因：uint8_t 上限 255，循环条件 `row < 339` 恒真 → `row++` 在 255 处回绕为 0。
- 可达性：`storeSaveScribe` 允许正文 14000 字节（≈4666 汉字）。28px 档
  `cols=(480-24)/28=16` → 4666/16 ≈ 292 行 > 255，**长作文必然触发**。
- 后果：行索引表 `s_scribeRow[256..]` 反过来覆盖 `s_scribeRow[0..]`，
  返回值 `row+1` 截断成 0 → 页数算错、正文被截断/错位。
- 修法：行号与返回值改 `uint16_t`/`unsigned int`，`scribeTotalPages()`、
  `drawScribeImpl()` 里的 `uint8_t bodyRows` 同步改。

**P1-1 `epd_probe.cpp` 探针引脚不切换**
- `tryPins()` 每组候选都 `SPI.begin(sck,-1,mosi,cs)` 但从不 `SPI.end()`；
  core `SPI.cpp:66` 是 `if (_spi) { return true; }` → **第二组起引脚根本没换**，
  6 组对照全部跑在同一组引脚上，探针结论不可信。
- 修法：每次 `SPI.begin()` 前先 `SPI.end()`。

**P1-2 EEPROM 密码只有 32 字节**
- `portal_impl.cpp:17` 读 4032..4063（32B），但 WPA2 口令上限 63 字符；
  `handleSetap()`（:112-113）写入时**无长度上限** → 33~63 字符口令存得下、
  读不回来，连不上网。SSID 同样无上限（IEEE 上限也是 32B）。
- 修法：写前校验长度（SSID ≤32B、密码 ≤63B），EEPROM 布局扩到
  SSID 4000..4031 / 密码 4032..4094，或改存 LittleFS。

**P1-3 `urlDecode()` 不支持通用 %XX**
- `portal_impl.cpp:58-90` 是一串固定 `%XX` 替换（只覆盖大写、且不含
  `%0A-%0F`/`%7B-%7E`），**中文 SSID 的 UTF-8 百分号编码（%E4%B8%AD）会被原样存下**，
  与 `restoreConfig` 注释"保留中文 SSID 的 UTF-8 字节"自相矛盾 → 连不上。
- 已确认 ESP32 core `WebServer` **不**对表单参数做 URL 解码
  （`WebServer.cpp` 里 `urlDecode` 只有声明、无调用点），所以固件这层必须自己写对。
- 修法：换成真正的通用解码（`%XX` → 字节 + `+` → 空格，大小写都收）。

**P1-4 `handleApiStatus()` JSON 转义不完整**
- `api_panel.cpp:323-333` 只处理 `"`、`\`、`\n` 和 UTF-8 直通，
  **未处理 `\r` `\t` 等控制字符** → 公告里带回车/Tab 会产出非法 JSON，
  前端 `r.json()` 直接抛异常。`sendErr()` 同样只转义 `\\` 和 `"`。

**P2 若干（优化项）**
- API 无请求体长度上限（`webServer.arg("plain")` 无限长）→ 大 POST 顶内存。
- `content_store.cpp:361/402` `tt.days/tt.periods = days.size()` 先截断后校验
  （现实取值下仍能拦住，但写法应改成先查 size）。
- `DynamicJsonDocument` 在 ArduinoJson 7.4.3 已标 `ARDUINOJSON_DEPRECATED`；
  且 v7 的 `JsonDocument` 用**动态增长的内存池**，`doc(16384)` 的容量参数
  实际被忽略（`compatibility.hpp` 里 `DynamicJsonDocument` 只是空壳子类），
  所以"16KB 池装不下 14000 字正文导致解析失败"的旧判断**不成立**，应改用 `JsonDocument`。
- `portal_impl.cpp` `setupMode()` 每次进配网都往全局 `ssidList` 追加 → 重复累积。
- `handleSetap()` 长度无校验（与 P1-2 同源）。

### 二、已验证为"没问题"的点（避免误改）
- **SPI 4MHz 达标**：`GxEPD2_EPD` 构造函数 `_spi_settings(4000000, MSBFIRST, SPI_MODE0)`
  → `beginTransaction` 后 `spiFrequencyToClockDiv` 换算 → 实际 4MHz。
  （注意：ESP32 core `SPISettings()` 默认值是 **1MHz**，但 GxEPD2 显式传了 4MHz，
  两者不冲突。）
- **SPI 引脚不被覆盖**：core `SPIClass::begin()` 开头 `if (_spi) return true;`，
  固件先 `SPI.begin(11,-1,10,9)`，GxEPD2 init 里的 `_pSPIx->begin()` 直接返回，
  自定义引脚保留；core 3.3.10-cn 的 `begin()` **不调 `spiAttachSS`**，
  所以 CS=9 由 `digitalWrite` 手动控制不会与外设冲突。
- **红/黑/白三色通路完好**：`U8g2_for_Adafruit_GFX.h:91` 的 `fg_color` 是
  uint16_t → `drawFastHLine` → `writeLine` → `writePixel` → `drawPixel` →
  `GxEPD2_3C::drawPixel`（`color == GxEPD_RED` 写 `_color_buffer`），0xF800 不截断。

### 三、雅黑换字体方案（已定档，未生成正式字库、未动固件）

**实测数据**（字库体积按**二进制**口径，非 .c 源码体积——八进制转义会让
文件大小虚高 ~2.8 倍，这是之前一次误判的根源）：

| 字体 | px | build | thr | v1 二进制 | 备注 |
|---|---|---|---|---|---|
| 黑体(现行) | 28 | 2 | 110 | 617,783 | 基线 |
| 黑体(现行) | 34 | 2 | 110 | 802,107 | 基线 |
| 黑体(现行) | 44 | 0 | 180 | 1,026,813 | 基线 |
| **雅黑** | 28 | 2 | 110 | 638,735 | +3.4% |
| **雅黑** | 34 | 2 | 110 | 834,982 | +4.1% |
| **雅黑** | 42 | 0 | 180 | 1,038,068 | 替代 44px |
| 雅黑 | 44 | 0/1/2 | 任意 | — | **失败**：`RLE Compress: Error, glyph too large` |
| 雅黑粗 | 44 | 0 | 180 | — | **失败**（同上） |

- **44px 是硬阻塞**：u8g2 v1 每个字形只有 1 字节尺寸字段 → 单字形 ≤255B。
  雅黑笔画比黑体密，44px 下几乎所有阈值都爆（只有 thr≥250 能过，
  但那会只剩笔画核心、字变得极瘦，不能用）。换 build mode 也救不回
  （build=3 虽能过但产物只有 74KB，等于没编字形）。
- **42px 可行**：thr=180 通过，体积比黑体 44px 只多 1.1%；
  `cols=(480-24)/42=10` 不变、`rows=(800-22-44)/42=17`（原 16）→ 每页多 10 字。
- **推荐总参数**：雅黑 28px/thr110/build2 + 34px/thr110/build2 + 42px/thr180/build0，
  总量 2,511,785 B vs 现行 2,446,703 B → **+2.7%**（固件 flash 21% → 约 21.5%）。
- **28/34px 阈值与黑体完全一致**，墨量实测雅黑比黑体多 12%（雅黑笔画更连续，
  二值化后反而更"实"），无需重调。
- **v1 解码已验证**：用 `v1_verify.Decoder`（逐行复刻桥接库解析器）对
  雅黑 28/34/42px 三个字库做像素级比对，**31 字全部一致**，
  advance 仍等于字号 → 等宽假设未破、桥接层无需改动。
  （比对时必须两边都裁到墨迹包围盒：build≥1 会把字形补齐到统一宽高。）
